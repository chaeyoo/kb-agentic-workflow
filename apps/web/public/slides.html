agentic workflow 뜯어보기

직접 만들어 보니, 생각보다 단순했습니다

"이미 아실 수도 있지만" 은 한 번만. 직접 뜯어본 경험 공유라는 톤.
5막 · ① 에이전트 루프

프레임워크 없이, 120줄이 전부

// apps/service/src/agent/loop.ts (요약)
const messages = [{ role: "user", content: input }];
for (let turn = 1; turn <= maxTurns; turn++) {
  const msg = await callModel({ system, tools, messages });
  messages.push({ role: "assistant", content: msg.content });

  if (msg.stop_reason !== "tool_use") return answer; // 끝

  const results = [];
  for (const call of toolUses(msg))
    results.push(await toolbox.call(call.name, call.input));

  messages.push({ role: "user", content: results }); // 다시 위로
}
// 상한 도달 → 추측하지 않고 실패로 끝냄 (사람이 넘겨받음)

모델에게 묻고 → 도구를 달라면 실행해서 돌려주고 → 반복

루프는 이벤트만 내보낸다. 웹 · CLI · 리플레이가 같은 이벤트를 그린다.

thinkingtool_calltool_result approval_requiredmessage_deltaerrordone
LangChain 같은 프레임워크를 일부러 안 씀. 루프 자체는 이게 전부라는 걸 보여 주려고. ① 대화 기록 ② 모델 호출 ③ 응답 추가 ④ 도구 없으면 끝 ⑤ 도구 실행 ⑥ 승인 필요 알림 ⑦ 결과 돌려주기 ⑧ 상한.

search_policies:
  언제 쓰나: 정책 질문을 받으면 가장 먼저.
    조건이 여러 개면 조건별로 따로 검색.
  쓰지 말 것: 섹션 키를 알면 get_policy_document.
  검색 팁: 핵심 명사 2~4개. 없으면 동의어로 재검색
    (미성년자/아동, 보호자/법정대리인)

MCP = 도구를 "원격 서버"로 표준화. 토큰 권한에 따라 보이는 도구가 다르다 (read 5개 / propose 11개). Internals 열기

TOOL_DESCRIPTIONS=v1 / v2 로 바꿔서 같은 질문의 도구 호출 패턴이 어떻게 달라지는지 비교 가능. MCP: 우리 에이전트도, 외주 개발자의 Claude Code/Cursor 도 같은 서버에 붙는다.

requiresApproval

도구 메타데이터에 표시. 이 도구는 승인 대기 상태만 만들고, 반영은 사람이 한다.

↩️

수정요청 → 재제안

사람이 이유를 적어 돌려보내면 에이전트가 그걸 읽고 다시 제안한다.

변경안은 기준 버전을 들고 온다 — 그 사이 정책이 바뀌었으면 거절(409). 사람 승인만이 새 버전을 만든다.

프롬프트로 "하지 마"라고 하는 것보다, 도구 자체를 안 주는 게 확실하다. 토큰 권한(read/propose)도 같은 원리.

5막 · ⑤ RAG

검색을 파이프라인이 아니라 "도구"로

일반 RAG이 프로젝트 (Agentic RAG)
검색 주체코드가 질문마다 한 번모델이 필요할 때, 검색어를 바꿔 가며 여러 번
검색 방식임베딩 벡터 유사도키워드 + IDF (정책서 수십 섹션이면 충분)
검색 단위임의 크기 청크정책 섹션 + 버전 → 정확한 출처 인용
근거가 없으면그럴듯하게 답하기 쉬움"근거 부족 / 문서 간 모순" 판정 → 티켓

정책서가 수백 개로 늘면 검색 구현만 벡터 · 하이브리드로 교체. 도구 인터페이스는 그대로.
