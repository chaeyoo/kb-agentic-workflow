# 05. 빌드 로그

커밋 순서대로 무엇을 왜 만들었는지 기록한다. `git log --reverse` 와 함께 보면 된다.

## Day 1 — 뼈대, 정책 검색, 에이전트 루프 (시나리오 1: 터미널 Q&A)

### 1. 워크스페이스 (`chore: pnpm 워크스페이스 뼈대 구성`)
- pnpm workspace 로 `apps/service`, `apps/mcp`, `packages/core` 를 나눴다.
- 빌드 단계가 없다. `tsx` 로 TypeScript 를 바로 실행한다. 데모 규모에서 번들러는 설명할 거리만 늘린다.

### 2. 도메인 모델과 저장소 (`feat(core): ...`)
- **결정: DB 를 쓰지 않는다.** 실사용 계획이 없고, 필요한 상태(정책 버전, 티켓, 실행 기록)는 JSON 파일 하나로 충분하다.
  - service 서버 한 프로세스만 파일에 쓴다. mcp 서버는 service REST API 를 호출하므로 동시 쓰기 문제가 없다.
  - 쓰기는 임시 파일에 쓰고 rename → 중간에 죽어도 파일이 깨지지 않는다.
  - 트레이드오프: Render 에서는 재배포 때 초기화된다. 데모는 매번 같은 시드에서 시작하므로 오히려 편하다.
- **섹션은 버전마다 레코드를 쌓는다.** `key`(membership.age)는 버전과 무관한 식별자, `id`(membership.age@2)는 특정 버전.
  답변 인용은 항상 `id` 를 쓴다 → "몇 버전을 근거로 답했는지"가 남는다.
- 시드 문서 5개에 **의도적인 결함**을 넣었다. 에이전트가 "모른다"고 말해야 하는 상황을 만들기 위해서다.
  - 모순: 회원 자격(만 14세 미만 가입 불가) ↔ 보호자 대리 동의(보호자 동의 시 가입 가능)
  - 모순: 결과 열람(19세 미만 자녀는 보호자가 동의 없이 열람) ↔ 보호자 대리 동의(14세 이상은 자녀 동의 필요)
  - 공백: 검진 예약 문서에 미성년자 본인 예약 규정이 없음
- **검색:** 형태소 분석기 없이 조사를 떼는 최소 처리 + IDF 가중치.
  - 문제: 처음엔 단순 빈도로 점수를 매겼더니 "검진", "예약"처럼 모든 섹션에 나오는 말 때문에 검진 예약 문서만 상위에 떴다.
  - 해결: IDF(드문 단어일수록 가중치↑)를 넣자 "14세", "미만"이 있는 섹션이 올라왔다.

### 3. service REST API (`feat(service): ...`)
- 정책 조회 API 만 있다. **정책 문서를 직접 수정하는 API 는 없다.** 변경은 변경안 → 사람 승인 경로로만 (Day 3).
- `.env` 는 Node 22 내장 `process.loadEnvFile` 로 읽는다. dotenv 의존성 불필요.

### 4. MCP 서버 (`feat(mcp): ...`)
- `@modelcontextprotocol/sdk` 의 Web Standard Streamable HTTP 트랜스포트 + Hono.
- **요청마다 서버 인스턴스를 새로 만든다 (stateless).** 이유: 호출자 토큰의 권한에 맞는 도구만 등록하려고.
  read 토큰으로 붙으면 쓰기 도구는 목록에 아예 없다. "권한 밖의 일은 도구를 주지 않는 것이 가장 확실한 통제."
- 도구 정의와 description 을 분리했다 (`descriptions/v1.ts`, `v2.ts`). 같은 질문을 v1/v2 로 돌려 도구 선택 차이를 보는 실험용.
- `requiresApproval` 은 도구 정의의 설정값이고 MCP `_meta` 로 클라이언트에 전달된다. 루프 코드에 도구 이름을 하드코딩하지 않는다.

### 5. 에이전트 루프 (`feat(agent): ...`)
- LangChain 같은 프레임워크 없이 Anthropic SDK 의 tool use 를 직접 쓴다. `loop.ts` 가 전부다 (~120줄).
- 루프는 이벤트만 내보낸다. CLI 도, 웹 UI 도, 리플레이도 같은 이벤트를 그린다.
- **우리 에이전트도 MCP 클라이언트다.** 도구를 코드로 직접 부르지 않고, 외주 개발자와 같은 MCP 서버에 토큰으로 붙어서 쓴다.
- 재시도는 SDK 내장 기능을 끄고 `llm.ts` 에서 직접 한다. 그래야 타임라인에 "⟳ 429 — 1초 후 재시도"가 보인다.
- CLI(`pnpm ask`)는 에이전트를 직접 돌리지 않고 service 의 `POST /api/ask` SSE 를 받아 출력만 한다.
  → 파일 저장소에 쓰는 프로세스가 service 하나로 유지된다.
- 검증: API 키 없는 환경에서는 Messages API 스트리밍 형식을 흉내 내는 가짜 서버(`ANTHROPIC_BASE_URL`)로
  재시도 → thinking → 검색 → 병렬 도구 호출 → 인용 답변 → AgentRun/QaSession 저장까지 확인했다.

## Day 2 — 보드, 정책 공백 티켓, 웹 UI (시나리오 2)

### 6. 칸반 보드 도메인과 API (`feat(board): ...`)
- 티켓 담당자는 사람 또는 Agent. **담당자를 Agent 로 바꾸는 순간 실행이 시작된다.** 별도 "실행" 버튼보다 팀 워크플로우에 자연스럽다.
- 담당자 없이 만든 정책 공백 티켓은 연결된 첫 섹션의 **문서 담당자**에게 자동 배정한다.
  모델에게 "담당자를 찾아서 배정하라"고 시키는 대신 규칙으로 처리 → 토큰도 줄고 결과도 결정적이다.
- 로그인 대신 이름 선택. 호출자는 `x-actor` 헤더로 전달한다 (데모용 — 실제라면 인증 토큰에서 꺼낸다).
- 에이전트의 MCP 호출에는 `X-Agent-Run-Id` 를 싣는다. 그래서 에이전트가 남긴 코멘트에서 "어느 실행이 남긴 건지" 타임라인으로 바로 갈 수 있다.

### 7. board 도구와 정책 공백 처리 (`feat(mcp): board 도구 6종 ...`)
- `update_ticket_status` 의 상태 값에 `done` 이 없다. **완료 판단은 사람의 몫**이고, 규칙을 프롬프트로 부탁하는 대신 도구 스키마에서 빼버렸다.
  에이전트가 done 을 보내면 MCP SDK 의 입력 검증 단계에서 거부된다.
- 정책 공백 처리 순서를 시스템 프롬프트에 적었다: 중복 확인(`list_open_questions`) → 있으면 코멘트, 없으면 `create_ticket` → 답변에 티켓 번호.
  description 에도 "create_ticket 직전에 반드시 list_open_questions" 를 적었다. 프롬프트와 description 양쪽에 두는 이유:
  외주 개발자의 Claude Code 는 우리 시스템 프롬프트를 모른다. **도구 description 이 유일하게 모든 클라이언트에 전달되는 지침**이다.
- read 토큰에는 쓰기 도구 4개가 보이지 않는다 (조회 5개만).

### 8. 웹 UI (`feat(web): ...`)
- React + Vite. 라우터, 상태관리, UI 라이브러리 없이 hash 라우팅과 CSS 만 사용했다.
- 에이전트 이벤트는 SSE(`EventSource`)로 받는다. 서버는 구독 시점에 지난 이벤트부터 다시 보내므로, 새로고침해도 타임라인이 처음부터 보인다.
  - 겪은 문제: 서버가 스트림을 닫으면 `EventSource` 가 자동 재연결해서 같은 이벤트를 다시 받는다 → `done` 이벤트를 받으면 클라이언트가 먼저 닫는다.
- 보드는 에이전트가 바꾸는 화면이라 2.5초 폴링으로 갱신한다. 웹소켓/보드 이벤트 스트림은 이 규모에서 과하다.
- 운영에서는 service 서버가 `apps/web/dist` 를 서빙한다 → Render 에 올라가는 웹 서버는 service, mcp 두 개뿐.
- 검증: 가짜 LLM 으로 Playwright 를 돌려 Q&A → 공백 티켓 생성 → T-4 Agent 배정 → In Review 이동 → 인용 링크로 정책서 섹션 강조까지 확인.

## Day 3 — 변경안 제안 → 사람 승인 → 새 버전 (시나리오 3), /internals

### 9. 정책 변경안 (`feat(proposals): ...`)
- **정책 문서가 바뀌는 경로는 "사람의 승인" 하나뿐이다.** `ProposalService.review(approve)` 안에서만 새 섹션 버전이 만들어진다.
  - 에이전트: MCP 에 승인 도구가 없다. REST 도 `x-actor` 가 에이전트면 403. 두 겹으로 막는다.
- 승인 시: 새 버전(active) 생성, 이전 버전 deprecated, 문서 버전 +1, 변경 이유에 "근거 + 변경안 번호 + 티켓 + 승인자"를 남긴다.
- **낙관적 잠금:** 변경안은 기준 버전(baseVersion)을 기억한다. 그 사이 섹션이 바뀌었으면 제안도 승인도 409.
  두 변경안이 동시에 승인 대기일 때 나중 것이 앞의 변경을 조용히 덮어쓰는 사고를 막는다.
- diff 는 줄 단위 LCS 를 직접 구현했다 (30줄). 섹션은 짧아서 성능 문제가 없고, 의존성을 하나 줄였다.

### 10. propose_policy_change / request_approval (`feat(mcp): ...`)
- 두 도구 모두 `requiresApproval: true`. 루프는 이 설정만 보고 `approval_required` 이벤트를 낸다 (도구 이름 하드코딩 없음).
- **결정: request_approval 뒤에 루프가 "기다리지" 않는다.** 승인 대기 상태를 만들고 실행을 끝낸다.
  - 사람의 검토는 몇 분~며칠 걸린다. 그동안 LLM 대화를 붙잡고 있으면 비용·타임아웃·서버 재시작 문제가 생긴다.
  - 대신 상태(티켓 Needs Approval, 변경안 pending)를 저장해두고, 수정요청이 오면 **새 실행**이 티켓 코멘트를 읽고 이어받는다.
    대화 기록이 아니라 보드가 기억 역할을 한다.
- 티켓 작업 지시를 [A] 사람의 결정이 있음 → 변경안 제안, [B] 결정 없음 → 조사/공백 티켓 으로 나눴다.

### 11. UI 와 /internals (`feat(web): ...`, `feat(internals): ...`)
- 카드 상세에 변경안 diff 와 승인 / 수정요청 / 거절. 수정요청·거절은 이유가 필수다 (에이전트가 다음 제안에 반영할 재료).
- 정책서 뷰어: 문서 버전 선택, 섹션별 이력과 버전 간 diff, 승인 대기 변경안 표시.
- `/internals`: 실행 기록(입력 프롬프트 원문, 도구 호출, 토큰, 타임라인)과 MCP 도구 표.
  도구 표는 service 가 **실제로 MCP listTools 를 호출한 결과**다. 발표에서 "모델이 보는 것이 정확히 이것"이라고 보여줄 수 있다.
  description v1/v2 를 나란히 놓고 비교할 수 있다.
- 검증: 가짜 LLM + Playwright 로 Q&A → T-5 공백 티켓 → 담당자 결정 코멘트 → Agent 에게 맡기기 → P-1(Needs Approval)
  → 수정요청 → 자동 재실행 → P-2 → 승인 → membership.age v3, 티켓 Done, 이력 diff 까지 확인.
