정책 에이전트 만들어 본 이야기

검진 운영하면서 겪은 문제와, 그걸 에이전트로 풀어 본 과정

데모에 나오는 정책서, 티켓, 사용자는 전부 가상 데이터입니다.

인사. 오늘 할 얘기는 두 가지. 만든 거 보여 드리기, 만들면서 알게 된 거 공유하기. 데모 데이터는 전부 지어낸 것 (외부 LLM으로 전송되기 때문에 실제 정책서는 안 씀).
만 14세 미만 사용자는
검진 예약을 혼자 할 수 있을까요? 바로 답할 수 있거나, 어느 문서를 봐야 하는지 아시는 분?
손 들어 보게 하고 잠깐 기다리기. "저도 이런 질문에 바로 답을 못 한 적이 많았어요." (데모 정책서에서는 회원 자격 정책과 보호자 동의 정책이 서로 다르게 적혀 있음. 뒤에서 보여 줌)

정책이 궁금하면 문서보다 코드를 먼저 찾아보게 되는 경우가 많았습니다.

검진 처음 시작할 때 기획도 외주, 개발도 외주였음. 그걸 우리가 이어받아서 지금까지 개선 개발하고 운영 중. 외주사를 탓하는 얘기가 아니라, 구조상 생기는 문제라는 톤으로.

각 항목 실제 겪은 예시 하나씩 짧게. 담당자가 바뀌면 그 사람이 알던 정책도 같이 사라진다.

  • 만들면서 agentic workflow를 직접 뜯어볼 수 있어서, 그 내용도 같이 공유하려고 합니다.

02

만든 것

만든 것

하는 일

기능내용
정책 질의응답질문하면 정책서를 찾아서 답하고, 근거가 된 문서·섹션·버전을 같이 보여 줌
공백 감지근거가 없거나 문서끼리 내용이 다르면, 추측해서 답하지 않고 담당자에게 티켓 생성
정책서 갱신티켓에 담당자가 결정을 남기면 에이전트가 변경안을 만들고, 담당자가 승인해야 반영
MCP 서버외주 개발자가 쓰는 Claude Code, Cursor에서도 같은 정책을 조회할 수 있게 공개
앞에서 말한 세 가지 문제랑 대응: 개발(조회), 정책 관리(공백 감지, 갱신), 운영(이력).
만든 것 · 구조
1. 개발자 AI 도구 → MCP (read 토큰, 조회만) 2. 질문 → 에이전트가 같은 MCP로 검색해서 답, 모순이면 티켓 3. 결정 코멘트 → 변경안 → 사람 승인 → 새 버전 개발자와 에이전트가 같은 MCP 서버를 쓰고, 토큰 권한만 다름. 정책을 직접 수정하는 도구는 없음.
만든 것 · 역할

누가 무엇을 하나

누가하는 일권한
개발자개발하면서 자기 AI 도구로 정책 조회read 토큰, 조회만 가능
에이전트공백·모순 발견 시 티켓 생성, 결정 내용으로 변경안 작성propose 토큰, 정책 직접 수정 불가
정책 담당자결정을 남기고, 변경안 승인 또는 수정요청웹 화면, 승인은 사람만 가능

개발자는 물어보기만 하고, 정책이 비어 있으면 그 질문이 담당자에게 가는 티켓이 됩니다.

만들면서 알게 된 것

"이미 아실 수도 있지만"은 앞에서 한 번 했으니 여기선 생략.
에이전트 루프

루프 자체는 120줄 정도였습니다

// apps/service/src/agent/loop.ts (요약)
const messages = [{ role: "user", content: input }];
for (let turn = 1; turn <= maxTurns; turn++) {
  const msg = await callModel({ system, tools, messages });
  messages.push({ role: "assistant", content: msg.content });

  if (msg.stop_reason !== "tool_use") return answer; // 끝

  const results = [];
  for (const call of toolUses(msg))
    results.push(await toolbox.call(call.name, call.input));

  messages.push({ role: "user", content: results }); // 다시 위로
}
// 횟수 상한에 걸리면 실패로 끝내고 사람에게 넘김

모델 호출, 도구 실행, 결과 전달을 반복하는 구조입니다.

프레임워크 없이 직접 짰고, 루프는 이벤트만 내보냅니다. 웹, CLI, 리플레이가 같은 이벤트를 받아서 그립니다.

thinkingtool_calltool_result approval_requiredmessage_deltaerrordone
LangChain 같은 프레임워크는 일부러 안 씀. 흐름을 직접 보여 주려고. 대화 기록 → 모델 호출 → 도구 요청 없으면 종료 → 있으면 실행 → 결과 붙여서 다시 호출.
도구와 MCP

도구 설명을 어떻게 쓰느냐에 따라 동작이 달라졌습니다

v1

search_policies:
  "정책을 검색합니다."

질문 문장 그대로 한 번 검색하고 끝내는 경우가 많았음

v2

search_policies:
  언제 쓰나: 정책 질문을 받으면 가장 먼저.
    조건이 여러 개면 조건별로 따로 검색.
  쓰지 말 것: 섹션 키를 알면 get_policy_document.
  검색 팁: 핵심 명사 2~4개. 없으면 동의어로 재검색
    (미성년자/아동, 보호자/법정대리인)

MCP로 도구를 서버에 올려 두면 토큰 권한에 따라 보이는 도구가 달라집니다. read 5개, propose 11개. Internals

TOOL_DESCRIPTIONS=v1 / v2 로 바꿔서 같은 질문의 도구 호출이 어떻게 달라지는지 비교 가능. 우리 에이전트도, 외주 개발자의 Claude Code/Cursor도 같은 서버에 붙음.
사람 승인 (HITL)

위험한 작업은 도구 자체를 주지 않았습니다

정책 수정 도구 없음

에이전트는 정책서를 직접 바꿀 수 없고 변경안만 만들 수 있음

requiresApproval

승인이 필요한 도구는 메타데이터로 표시. 도구는 승인 대기 상태만 만들고 반영은 사람이 함

수정요청

담당자가 이유를 적어 돌려보내면 에이전트가 읽고 다시 제안

변경안에는 기준 버전이 들어 있어서, 그 사이 정책이 바뀌었으면 거절됩니다(409).

프롬프트로 "하지 마"라고 하는 것보다 도구를 안 주는 쪽이 확실했음.
실행 기록

에이전트가 왜 그렇게 했는지 기록을 남겼습니다

AgentRun

실행마다 이벤트 전체, 사용한 도구, 토큰, 소요 시간, 모델, 도구 설명 버전 저장

/internals 타임라인

생각, 도구 호출, 결과, 답변을 시간순으로 확인. 답이 이상하면 여기서 원인을 찾음

리플레이

녹화한 실행을 원래 속도로 다시 재생. 발표 당일 API 장애 대비용

같은 이벤트

웹, CLI(pnpm ask), 리플레이가 모두 같은 이벤트 스트림(SSE)을 사용

에이전트는 같은 질문에도 매번 조금씩 다르게 움직여서, 기록이 없으면 디버깅이 거의 불가능했음.
검색 (RAG)

검색은 모델이 필요할 때 부르는 도구로 뒀습니다

흔히 쓰는 RAG이번 프로젝트
검색 시점질문마다 코드가 한 번 검색모델이 필요할 때 검색어를 바꿔 가며 여러 번
검색 방식임베딩 벡터 유사도키워드 + IDF (정책서 규모가 작아서 충분)
검색 단위일정 길이로 자른 청크정책 섹션 + 버전 (출처를 정확히 달기 위해)
근거가 없을 때그럴듯하게 답하는 경우가 있음근거 부족, 문서 간 모순으로 판단하고 티켓 생성

정책서가 많아지면 검색 구현만 벡터 검색으로 바꾸면 되고, 도구 형태는 그대로 쓸 수 있습니다.
